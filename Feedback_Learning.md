# Squish — Personalized Learning & User Feedback Architecture

## 1. Executive Summary

Squish incorporates a safety-first, on-device **Personalized Learning Engine** (`PersonalizedLearningEngine.kt`) designed to continually adapt threat classification to individual user habits without compromising device security or introducing catastrophic vulnerability blindspots.

In classical machine learning deployment, user feedback loops frequently succumb to:
1. **Adversarial Manipulation:** Attackers tricking victims into marking phishing domains or smishing attacks as "Safe".
2. **Global Model Poisoning:** Bad telemetry contaminating shared cloud models.
3. **Irreversible State Drift:** Accidental user misclassifications permanently disabling security protections.

Squish resolves these challenges using an isolated, reversible, on-device feedback architecture governed by deterministic security guardrails.

## 3. Core Principles & Safeguards

### 3.1 Strict Security Guardrails (Non-Overridable)
Under no circumstances may user feedback override a message containing verified scam mechanics. Even if a user previously marked a sender as trusted or safe:
- **Credential / OTP Demand:** If the message requests a verification code, PIN, password, or KYC update (`CREDENTIAL_REGEX`), trust adjustments are bypassed and the message is flagged.
- **Untrusted / Suspicious Domain:** If the message links to an unverified external URL, IP address hostname, or deceptive homoglyph domain, the risk score is preserved.
- **Payment Demand:** Any urgent demand for wire transfers, gift cards, or crypto transfers cannot be suppressed by trusted sender status.

### 3.2 Reversible Actions & Feedback History
Every feedback action is stored in the Room database (`feedback` table) and mirrored to Firestore:
- `originalPrediction`: The initial score and verdict generated by the AI model.
- `correctedClassification`: The user's label (`FALSE_POSITIVE`, `CONFIRMED_THREAT`, etc.).
- `comments`: Optional user rationale.
- `timestamp`: Time of submission.

Users can view their entire feedback history in the detailed analysis screen and tap **Undo Feedback** at any time. When feedback is removed:
- The sender's trust weight is immediately recalibrated.
- Any adjusted threat records revert to their baseline model evaluation.

### 3.3 Trusted Sender Repository
The `trusted_senders` table records verified senders (e.g., family contacts, company communication channels) with an explicit trust level:
- Trust level `TRUSTED` provides a targeted score dampening (-40 to -50 risk points) for routine conversational messages.
- Trust level `UNTRUSTED` / `BLOCKED` immediately treats messages as high-attention/quarantined.
- Guardrails ensure that if a trusted sender's account or phone number is spoofed or compromised (e.g. sending malicious download links), the guardrails trigger immediately to protect the user.

## 4. Telemetry Minimization & Privacy Guarantees

In accordance with strict privacy-preserving ML design:
- Raw message bodies, passwords, account numbers, and personal identities are **never transmitted** to cloud telemetry servers.
- Feedback telemetry transmits only anonymized token frequency statistics, model version hashes, and classification confusion matrices.
- Users have full granular control in **Settings & Privacy** to toggle `Contribute Anonymized Threat Telemetry` on or off with zero impact on local detection performance.
