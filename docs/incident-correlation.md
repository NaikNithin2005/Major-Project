# Threat Correlation Engine & Heuristic Grouping Logic

## 1. Objectives & Boundaries

The Threat Correlation Engine in Phase 15 enables SOC operators to connect related smishing and quishing detections into coherent security incidents without creating false positives or aggressively merging unrelated detections.

### Core Policy: Conservative Provenance
1. **Detections are evidence, not auto-merged clusters:** The system suggests correlation candidates; an authorized administrator confirms the relationship.
2. **Deterministic Indicators Only:** Correlation relies on verified indicators (exact normalized URLs, canonical domains, and verified campaign identifiers).
3. **No Speculative Merging:** Superficial text similarity, shared public cloud IPs (e.g., AWS, Cloudflare CDN), or common hosting providers are explicitly rejected as standalone correlation signals.

---

## 2. Correlation Signals & Confidence Levels

| Signal Type | Description | Confidence Level | Rationale |
| :--- | :--- | :--- | :--- |
| `MATCHING_URL` | Exact normalized URL string match across SMS or QR detections | `CONFIRMED` | Two devices scanning the exact same phishing link indicates identical attack payload. |
| `MATCHING_CAMPAIGN` | Matching campaign tag generated by backend clustering or threat intel feed | `CONFIRMED` | Confirmed phishing kit or campaign identifier (e.g. `CAMP_CHASE_2026_01`). |
| `MATCHING_DOMAIN` | Canonical domain match (e.g., `secure-login-chase-update.com`) | `LIKELY` | Shared attack infrastructure; requires operator verification against multi-tenant domains. |
| `MANUAL_CORRELATION` | Direct administrative linkage based on external intelligence or forensic analysis | Operator Selected | Administrative discretion based on offline context. |

## 3. Correlation Workflow

```text
1. Incident Dossier Open
       ↓
2. Extract Known Indicators from Currently Linked Threats:
   - Set of Normalized URLs
   - Set of Malicious Domains
   - Set of Campaign Identifiers
       ↓
3. Query Unlinked Threat Events (Last 60 Days)
       ↓
4. Filter Candidate Matches Against Known Indicators
       ↓
5. Display Candidate Stream with Signal & Confidence Badge
       ↓
6. Operator 1-Click Link or Rejection
       ↓
7. Append Event to Incident Audit Trail
```

### 3.1 Unlinking & Correction
If an administrator incorrectly correlates a detection to an incident, the operator can decouple the threat at any time via `DELETE /api/v1/admin/incidents/{incident_id}/threats/{threat_event_id}`. This action:
- Deletes the record from `incident_threat_links`.
- Retains the underlying threat event untouched.
- Records a `THREAT_UNLINKED` event in `incident_events` for auditability.
- Restores the threat event to candidate status for other investigations.

---

## 4. Query Bounds & Performance

To prevent database contention during large-scale telemetry ingestion:
- Candidate search window is bounded to the preceding **60 days**.
- Candidate result set is limited to **100 candidates**.
- Indexed columns on `threat_events` (`url_metadata`, `timestamp`, `campaign_id`) are utilized.
- Deduplication ensures threats already linked to the current incident are excluded via `NOT IN (linked_threat_ids)`.
